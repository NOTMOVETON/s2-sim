# Known Bugs

## [OPEN] Дрожание робота и плавание лидарной линии на наклонных поверхностях

**Симптомы:**
- Робот визуально трясётся на рампе при вращении (особенно при одновременном скольжении вниз)
- Линия пола от лидара «плавает» при повороте робота на наклонной поверхности

**Ожидаемое поведение:** Робот стоит стабильно на рампе. Линия пола в лидарном скане стабильна.

**Диагностика:**

GravityPlugin (фаза 3e) снапит `z = ground_z + radius` **точно** — проникновение ≈ 0.
После этого `check_sphere_all()` в фазе 3h **не находит контактов**, нет walkable-нормали.

Alignment-код полагался на collision contacts для получения нормали поверхности.
При отсутствии контактов → `pitch = roll = 0`.

Результат: pitch/roll фликерят тик-за-тиком между нормалью рампы (редкий fp-контакт) и нулём.

Последствия фликера:
1. Плоскость скана лидара дрожит → плавание линии пола
2. `R.transpose() * slide_velocity_` в GravityPlugin нестабилен → нестабильный body velocity → встряска

**Что было попробовано:**

1. **`p / nz` вместо `nz * p` для Z push-out** — математически корректнее (полное снятие проникновения), но не затрагивает корень (alignment из contacts).

2. **Alignment через `find_support_surface()`** (down-raycast, не зависит от проникновения) — изменено в `sim_engine.hpp` фаза 3h, но не помогло на практике.

**Предположительная причина:** Предположительно проблема глубже — в порядке фаз. GravityPlugin (3e) снапит Z для **старого** XY, затем кинематика (3f) меняет XY, и Z для нового XY оказывается неверным. Даже корректный `find_support_surface` в 3h читает нормаль для **нового** XY, но снап Z уже произошёл для **старого** XY. Осцилляция возникает из-за того, что снап и кинематика разделены одной фазой.

**Где искать:**
- `workspace/s2_core/include/s2/sim_engine.hpp` — фаза 3e (плагины, GravityPlugin), 3f (кинематика), 3h (коллизии + alignment)
- `workspace/s2_plugins/include/s2/plugins/gravity.hpp` — `find_support_surface` + snap

**Возможное направление решения:** Перенести GravityPlugin (или только его snap-фазу) в 3g (Surface snap — сейчас пустая фаза) — **после** кинематики. Тогда snap происходит для правильного XY. Либо в GravityPlugin при snap учитывать предсказанное XY (current_pos + velocity * dt).

## [OPEN] Превью нового агента не отображается сразу после размещения в редакторе

**Симптом:** После клика на сцену в режиме размещения агента форма открывается, но полупрозрачный бокс нового агента не виден. Бокс появляется только при изменении любого поля формы (x, y, yaw, размер, цвет).

**Ожидаемое поведение:** Сразу после клика превью-бокс отображается на выбранной позиции. При изменении полей формы — обновляется в реальном времени.

**Что работает:** Полупрозрачный бокс при наведении мышки в режиме размещения (`agent_place_preview`) работает корректно.

**Что было попробовано:**
1. Исключение `agent_edit_*` из SSE-очистки мешей в `updateScene` (`app.js:1050`) — не помогло.
2. Явный вызов `refreshNewAgentPreview()` в конце `openAgentForm` после установки всех значений формы — меш создаётся, но не отображается до первого `input`-события.

**Предположительная причина:** `refreshNewAgentPreview()` вызывается до того как браузер успевает отрисовать фрейм, либо что-то в цикле `updateScene` удаляет или скрывает меш раньше первого рендера. Точная причина не установлена.

**Где искать:** `workspace/s2_visualizer/web/js/app.js` — функции `openAgentForm`, `refreshNewAgentPreview`, `updateScene` (~строка 1050).

## [OPEN] Задача 19: reload не переинициализирует ROS2 транспорт

**Симптом:** После загрузки новой сцены через "Scenes → Load" ROS2-ноды и топики не пересоздаются. Если новая сцена имеет других агентов или другие `domain_id` — транспортный слой остаётся от предыдущей сцены.

**Когда проявляется:** Только при `transport: type: ros2`. При `type: stub` не заметно.

**Обходной путь:** Полный рестарт Docker-контейнера.

**Где искать:** `workspace/s2_visualizer/src/main.cpp` — `SimEngineCommandAdapter::on_load_scene()`. После `engine_->load_world()` нужен вызов `transport_bridge_->reinit(engine_->world())`, но `transport_bridge_` недоступен в адаптере (создаётся в `main()`).

## [OPEN] Сильные задержки при включённых overlay-плагинах (траектория, путь)

**Симптомы:**
- При 3 включённых `trajectory_recorder` / `path_display` задержка drag-гизмо достигает десятков секунд и более
- Команды `diff_drive` (`plugin_input`) отрабатывают с задержкой 10–60 секунд
- Чем больше агентов с включёнными траекториями — тем хуже

**Диагностика:**
Каждый SSE-фрейм (30fps) содержит полный снапшот включая все точки траекторий
(до 300 точек × 3 координаты на агента). При 3 агентах — ~900 3D-точек в JSON каждые 33ms.
Отправка больших сообщений потенциально блокирует мьютексы, которые также удерживает
поток симуляции при `publish()`, и HTTP-handler при командах.

**Попытки решения (не помогли):**

1. **Throttle plugins_data**: включать данные плагинов только раз в 10 кадров (~3Hz вместо 30Hz).
   Изменён `snapshot_to_json()` — добавлен параметр `include_plugins`.
   В `handle_pending_snapshots()` счётчик `snap_counter_` определяет когда включать.

2. **MSG_DONTWAIT в send()**: заменить блокирующий `send()` на неблокирующий.
   Если буфер сокета занят — кадр дропается вместо блокировки потока.

3. **Освобождение snapshot_mutex_ до сериализации**: основная гипотеза —
   JSON-сериализация (медленная) происходила внутри `snapshot_mutex_`, блокируя
   поток симуляции. Исправлено: снапшот копируется под мьютексом, мьютекс отпускается,
   затем сериализация. Затронуто: `handle_pending_snapshots()`, `force_broadcast_latest()`,
   `send_snapshot_now()`.

4. **Вынесение handle_pending_snapshots() из accept-цикла**: accept-цикл конкурировал
   с SSE-потоками за обработку снапшотов, что могло блокировать приём команд.

5. **JS-кэш overlay-линий**: добавлен `overlayLineCache` — BufferGeometry Three.js
   не пересоздаётся если количество точек и последняя точка не изменились.

**Возможные направления дальнейшего исследования:**
- Замерить реальный размер SSE-сообщений и пропускную способность (`tcpdump` / `ss -i`)
- Проверить не является ли узким местом сам JS (`performance.now()` вокруг `updateScene`)
- Рассмотреть бинарный формат (MessagePack / protobuf) вместо JSON для траекторий
- Рассмотреть отдельный SSE-поток только для позиций агентов (лёгкий, 30fps)
  и отдельный polling-endpoint для overlay-данных (тяжёлый, 2-3fps)
- Ограничить `max_points` в `trajectory_recorder` до 50-100 точек пока проблема не решена
